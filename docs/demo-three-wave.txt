REEF DEMO PLAYBOOK — 3-WAVE INCIDENT LAB (ORG REPO + GITHUB + VERCEL + SENTRY + SLACK)
================================================================================

Purpose
-------
Build a fresh GitHub org repo with THREE controlled production waves so Reef/Coral
can correlate real data across sources. Two waves intentionally break production
(different error types); one wave is clean (control).

Reef's strongest join (template + LLM planner):
  github.pulls.merged_at  <=  sentry.issues.first_seen
  + vercel.deployments around the same window
  + slack channel #incidents (metadata; post human-readable incident text)

Timeline rule: for each wave, always:
  1) Open PR → review → merge to main
  2) Wait for Vercel production deploy to finish
  3) Hit the broken endpoint (waves 2–3) or health only (wave 1)
  4) Confirm events in Sentry
  5) Post a short message in Slack #incidents
  6) Run Reef investigation (note deploy id + time)

Allow 5–15 minutes between merge and investigation so Coral/Sentry indexes data.

PART 1 — CREATE GITHUB ORG + REPO
================================================================================

1.1 Create organization (if you don't have one)
    - https://github.com/organizations/plan
    - Name: reef-demo-org (or similar)
    - Note the org slug (URL: github.com/reef-demo-org)

1.2 Create repository
    - New repo: reef-incident-lab
    - Private or public (public is easier for hackathon demos)
    - Add README, .gitignore (Python), license optional
    - Default branch: main

1.3 GitHub token for Reef/Coral (org access)
    - Settings → Developer settings → Fine-grained personal access token
      OR classic PAT with repo scope for the org
    - Scopes: read access to metadata, pull requests, contents (repo)
    - Save as GITHUB_TOKEN in backend/.env

1.4 Recommended minimal app (FastAPI on Vercel)
    Create backend/app structure in the repo:

      reef-incident-lab/
        api/
          index.py          # Vercel serverless entry (or main.py + vercel.json)
          requirements.txt  # fastapi, sentry-sdk[fastapi], uvicorn
        vercel.json
        README.md

    api/index.py should expose:
      GET  /health              → always 200 {"status":"ok","wave":N}
      POST /checkout            → wave 1 OK; wave 2 raises TypeError
      POST /auth/login          → wave 1 OK; wave 3 raises 401/validation error
      GET  /deploy-info         → returns DEPLOY_WAVE env for debugging

    Use environment variable on Vercel per deploy:
      DEPLOY_WAVE=1 | 2 | 3
    (Set in Vercel → Project → Settings → Environment Variables → Production)

    Sentry init in the app (required for real errors):
      import sentry_sdk
      sentry_sdk.init(dsn=os.environ["SENTRY_DSN"], traces_sample_rate=1.0)

1.5 Branch protection (optional but realistic)
    - Settings → Branches → Add rule on main
    - Require 1 PR review before merge (use a second account or self-review via org policy)

PART 6 — THREE WAVES (detailed choreography)
================================================================================

Use separate PRs. Merge only when ready for that wave's story.
Space waves at least 30–60 minutes apart for clean timelines.


--------------------------------------------------------------------------------
WAVE 1 — CLEAN BASELINE (control: no regression)
--------------------------------------------------------------------------------

Goal: Establish good deploy + merged PR + empty/minimal Sentry noise.

GitHub
  - Branch: wave-1-baseline
  - Change: Add /health, wire Sentry, DEPLOY_WAVE=1 behavior (checkout + auth OK)
  - PR title: "wave-1: baseline health and observability"
  - Get 1 approval → Merge to main
  - Record: PR number ____ , merge time ____

Vercel
  - Set DEPLOY_WAVE=1 in Production env (if not in code default)
  - Wait for production deploy READY
  - Record: dpl________________ , deploy time ____

Validation
  - curl https://<prod>/health → 200
  - curl -X POST https://<prod>/checkout -d '{}' → 200
  - Sentry: no new fatal/error issues (or resolve any test noise)

Slack
  - Post wave-1 message with dpl_ id

Reef test query (expect low severity / weak root cause):
  "Investigate production after baseline deploy — any regressions across GitHub,
   Sentry, Slack, and Vercel?"
  Or paste vercel_url: dpl_<wave1>


--------------------------------------------------------------------------------
WAVE 2 — CHECKOUT REGRESSION (TypeError / HTTP 500)
--------------------------------------------------------------------------------

Goal: Obvious code regression tied to merge time; Sentry error type A.

GitHub
  - Branch: wave-2-checkout-bug
  - Change: Introduce bug when DEPLOY_WAVE=2, e.g.:
      amount = None
      total = amount + 10   # TypeError on POST /checkout
  - PR title: "wave-2: refactor checkout totals (INTENTIONAL BUG FOR DEMO)"
  - Review comment: "LGTM for demo" → Merge
  - Record: PR number ____ , merge time ____

Vercel
  - Set DEPLOY_WAVE=2 in Production env variables
  - Redeploy production (merge triggers build)
  - Record: dpl________________

Trigger errors (10–20 requests)
  curl -X POST https://<prod>/checkout \
    -H "Content-Type: application/json" \
    -d '{"cart_id":"demo-1","amount":null}'

Sentry (expected)
  - New issue: TypeError (or similar)
  - Level: error or fatal
  - Note issue shortId: __________

Slack
  - Post wave-2 incident message referencing dpl_ and Sentry id

Reef test query (expect PR ↔ Sentry correlation):
  "Why did checkout start returning 500 errors after the last production deploy?"
  Or:
  vercel_url=dpl_<wave2> + query about checkout TypeError

Expected Reef behavior:
  - Planner iter 1+: join github.pulls + sentry.issues
  - Judge: hypothesis naming wave-2 PR and TypeError
  - Root cause mentions PR # and error message


--------------------------------------------------------------------------------
WAVE 3 — AUTH REGRESSION (different error class: 401 / ValueError)
--------------------------------------------------------------------------------

Goal: Second break pattern so Reef must not only repeat wave-2 story.

GitHub
  - Branch: wave-3-auth-bug
  - Change: When DEPLOY_WAVE=3, e.g.:
      - Reject all logins with 401 Unauthorized, OR
      - raise ValueError("invalid credentials schema") on /auth/login
  - Fix checkout from wave 2 OR leave broken — your choice:
      * Recommended: FIX checkout in wave 3 so only auth breaks (clearer signal)
  - PR title: "wave-3: auth middleware strict mode (INTENTIONAL BUG FOR DEMO)"
  - Merge after review
  - Record: PR number ____ , merge time ____

Vercel
  - Set DEPLOY_WAVE=3
  - Record: dpl________________

Trigger errors
  curl -X POST https://<prod>/auth/login \
    -H "Content-Type: application/json" \
    -d '{"email":"user@demo.com","password":"wrong"}'

Sentry (expected)
  - NEW issue distinct from wave 2 (401 / ValueError / AuthenticationFailed)
  - shortId: __________

Slack
  - Post wave-3 message — explicitly say "different from wave 2 checkout incident"

Reef test query:
  "Users cannot authenticate after the latest merge — correlate PRs, deploys,
   and fatal errors."
  Or vercel_url=dpl_<wave3>

Expected Reef behavior:
  - Should surface wave-3 PR, not wave-2, if timestamps/order correct
  - Different error_message in sentry.issues row

PART 10 — TROUBLESHOOTING
================================================================================

  No github.pulls rows
    → GITHUB_OWNER/REPO wrong; token lacks org access; merge was to wrong branch

  No sentry.issues rows
    → SENTRY_DSN not set on Vercel; errors not triggered; wrong SENTRY_ORG

  Reef correlates wrong PR
    → Waves too close together; add 30+ min between merges or use vercel_url filter

  Coral setup fails
    → Re-run setup_coral_sources.sh; check GLIBC image (python:3.12-slim-trixie)

  CORS / Failed to fetch
    → CORS_ORIGINS includes https://usereef.grandkojo.my; force-recreate api container

  LLM planner/judge not used
    → ANTHROPIC_API_KEY set + docker compose up -d --force-recreate api

PART 11 — OPTIONAL: MINIMAL api/index.py PSEUDOCODE
================================================================================

  import os
  from fastapi import FastAPI, HTTPException
  import sentry_sdk

  sentry_sdk.init(dsn=os.environ["SENTRY_DSN"])
  app = FastAPI()
  WAVE = int(os.environ.get("DEPLOY_WAVE", "1"))

  @app.get("/health")
  def health():
      return {"status": "ok", "wave": WAVE}

  @app.post("/checkout")
  def checkout(body: dict):
      if WAVE == 2:
          x = None
          return {"total": x + 1}  # TypeError
      return {"total": 99}

  @app.post("/auth/login")
  def login(body: dict):
      if WAVE == 3:
          raise HTTPException(status_code=401, detail="invalid credentials")
      return {"token": "ok"}

Copy this into reef-incident-lab and adapt to your Vercel Python handler pattern.
